# Evaluation runbook

## Purpose

This is the one supported first-run evaluation for the WriteGuard release candidate:

```powershell
pnpm install --frozen-lockfile
pnpm evaluate:local
```

It requires Node.js 20+ and pnpm. It does not require OpenAI, Stripe, PostgreSQL, Docker, or a `.env` file. Do not add credentials: the path is intentionally self-contained.

## What happens

The command prepares a clean temporary consumer, packs and installs `@closure/writeguard` and `@closure/writeguard-generator`, and then follows:

`Tool → Analyze → Review → Approve → Generate → Verify → Integrate`

1. A direct MCP-style refund tool is normalized.
2. A deterministic, runtime-validated recorded analysis fixture is loaded. It identifies GPT-5.6 compatibility, remains `recommendation_only`, and is not represented as a live response.
3. An unapproved review draft is created.
4. A developer identity explicitly acknowledges enforcement and the provider hook, then approves the review.
5. The generator emits a wrapper, provider boundary, failure test, verification bundle, and manifest.
6. Safe static verification checks the manifest-owned artifacts, digest chain, imports, credential patterns, provider shape, and public-surface compilation.
7. The evaluator explicitly opts into the manifest-owned generated test. It does not run a target package script.
8. A deterministic simulated provider shows two effects from unsafe retry and one effect from guarded execution.
9. The public six-scenario adapter conformance kit runs.
10. A versioned CI policy evaluates named receipt requirements.
11. A human summary is rendered from the validated evidence objects.

## Evidence

The command writes ignored, sanitized local evidence:

- `.writeguard/evaluation-report.json`
- `.writeguard/evaluation-summary.md`
- `.writeguard/evaluation-static-verification.json`
- `.writeguard/evaluation-generated-test-verification.json`
- `.writeguard/evaluation-policy.json`
- `.writeguard/evaluation-adapter-conformance.json`
- `.writeguard/evaluation-runtime.json`

The JSON report is the source of truth. The Markdown summary is derived from it. Absolute user paths, raw provider errors, credentials, and raw sensitive inputs are rejected from the report and summary contracts.

## Interpreting the result

A passing evaluation means the exact packed artifacts completed the documented simulated journey and met the checked evaluation policy. It does not mean:

- the recorded analysis was generated by a live call during the run;
- the historical 9/9 live gate retained the exact raw output used as this fixture;
- a real provider was called;
- Stripe semantics were verified;
- production storage or cross-process recovery was exercised by this evaluator;
- the child process is a security sandbox;
- digest bindings establish authorship or authenticity;
- a new external developer completed the journey in under ten minutes.

The expected real-provider level is `not_run`. The next integration step is to implement a reviewed provider boundary, configure durable PostgreSQL-backed storage, and run provider-specific test-mode conformance.

## Timing

Record three values separately:

| Measurement | Meaning | Current status |
|---|---|---|
| Automated execution | Wall-clock time printed by `evaluate:local`; not onboarding time | Produced on every run |
| Maintainer clean-room | A maintainer follows this runbook from a clean checkout | Pending a recorded timed session |
| External-developer | A new developer completes the journey without direct assistance | Pending external testing |

Do not use automated runtime to claim the under-ten-minute developer outcome.

## CI

`.github/workflows/evaluation.yml` runs the same command on declared Ubuntu and Windows runners and preserves `.writeguard/evaluation-*` artifacts. Its structure is locally checked by `pnpm validate:evaluation-ci`. A local structural pass is not evidence that GitHub-hosted runners executed; remote CI status remains unverified until the workflow is pushed and completes.

## Optional Stripe test-mode follow-up

Iteration 5 does not require a Stripe key. If a fresh, rotated test secret is available, start the documented PostgreSQL service and load the value only into the current process:

```powershell
docker compose up -d postgres
pnpm db:migrate
$secureKey = Read-Host "Fresh Stripe test secret" -AsSecureString
$env:STRIPE_SECRET_KEY = [Net.NetworkCredential]::new("", $secureKey).Password
pnpm demo:stripe
Remove-Item Env:STRIPE_SECRET_KEY
docker compose stop postgres
```

Never paste the secret into chat, command arguments, source, fixtures, logs, or a committed environment file.
